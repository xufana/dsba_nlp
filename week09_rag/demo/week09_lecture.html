Block 00 · the task

A query against a collection

The task: a query q against a fixed collection D → a ranking of what already exists.

Score every document s(q,d) → sort → return the top k.

Classification and retrievalone label, or an order over the collection
One object → one label, or a query and a whole collection → an order over it.
In detail

The task. A collection of documents D, fixed in advance and large; a query q, which arrives at run time and is short. Return the documents of D in order of how well they answer q. Not one label, not a generated text: a ranking of what already exists. Whatever the method, the mechanics are the same: give every document a score s(q,d), sort, return the top k.

Classification reads one object and outputs one of a fixed set of labels. Retrieval reads a query and a whole collection and outputs an order over the collection; the label set is the collection itself, and it changes when a document is added.

Why it is a problem of its own:

  • the collection is huge → per-document work happens before the query
  • query and document are written differently
  • relevance is a judgement about a pair, made by a person
A question and its postwhich of its words the post contains
A gonzo_ML question against its post: the words the question is about are not in the post.
In detail

Three things make it a problem of its own:

  • the collection is too large to look at every document with an expensive model for every query: whatever is computed per document must be computed before the query arrives;
  • the query and the documents are written differently: a short question against long documents, in other words — they often share few of the words that matter;
  • "relevant" is a judgement about a pair (query, document), made by a person; there is no label on a document alone.

A question from a golden set over {n_posts} posts of the Russian Telegram channel gonzo_ML, word by word against the post that answers it ({ex_post_words} words). Green — the word occurs in the post; orange — only another form of it (the same first five letters); grey — absent. The words the question is about are in the third group. Word matching over whitespace tokens did not put this post into its top 10. On this corpus a question has a median of {q_words_median} words, a post {doc_words_median}.

The vocabulary for the rest of the page: the collection and its documents (a page, a paragraph, a chunk of a post); the query; the index — whatever is precomputed over the collection so that search is fast; the retriever — the function from a query to a ranked list; relevance judgements (qrels) — the pairs labelled relevant.

A ranking always has a first document — even when the answer is not in the collection.

No answer, still a ranking«Как сварить борщ?» against the posts
A question the channel cannot answer still gets a confident top 3.
In detail

Retrieval also has to know when it has nothing. A web engine can always show something; a system that answers from a company's documents must notice that the answer is not in the collection. A ranking does not say that by itself: there is always a first document.

Block 01 · what "good" means

Relevance and the metrics

  • Relevance — a person's judgement on a pair (query, document): 0 / 1, or graded 0 / 1 / 2
  • nobody judges everything: only the pool — the union of several systems' top k
  • outside the pool = counted as not relevant
Poolingonly what some system retrieved gets judged
① three systems retrieve → ② only their union is judged → ③ a fourth system's new finds count as misses.
In detail

Where relevance comes from. People read pairs (query, document) and mark them relevant or not — sometimes on a scale, 0 / 1 / 2. Judging every document for every query is impossible on a real collection, so test collections are built by pooling: run several systems, take the union of their top results, judge only those, and treat the rest as not relevant. This is the Cranfield paradigm, from the 1960s, and every number below inherits its two weak spots: unjudged documents count as misses, and the pool favours the systems that built it.

The picture is the procedure of a test collection (TREC, and every golden set built the same way). Several systems run every query; the union of their top k is the pool; people judge only the pool. A new system is then scored against those judgements: a document it found that nobody else did was never judged, and the metrics count it as not relevant — whether it is or not. Two consequences, both visible here: the new system's precision is underestimated, and R, the number of relevant documents the metrics divide by, is the pool's, not the collection's. The pool favours the systems that built it (Zobel, 1998); bpref, on the last tab of the metrics, is the metric designed for exactly this.

For RAG: a golden set — question → the id of the document that answers it, not a quote.

In detail

For RAG the judgements are usually cheaper: a "golden set" of questions, each with the passage or the post that answers it. Write it down as a document id. A quote that has to be matched against the retrieved text by fuzzy similarity is a second, hidden retriever inside your metric.

One query → a ranked list d1,d2,… with grades reli; R — relevant documents in the collection.

Every metric models a reader: who reads how much of the list, and what counts.

Ranking metricsone list, ten metrics

P@k=1k∑i=1kreli — the share of relevant documents among the first k.

Reader: looks at all k results. Blind spot: a ceiling — with R<k relevant documents the best possible is R/k: one relevant document, P@10≤0.1 for a perfect retriever. The order inside the top k does not count.

R-precision=P@R — precision at the depth of the number of relevant documents.

Reader: wants all R of them. Fixes the ceiling of P@k: a perfect ranking always scores 1. Blind spot: needs R, which under pooling nobody knows; the order inside the first R does not count.

Recall@k=1R∑i=1kreli — the share of the relevant documents that made it into the top k.

Reader: takes the top k as a set — a prompt with k passages. Blind spot: only grows with k and reaches 1 at k=|D| for any retriever: compare systems at one k. Divides by R, which the pool underestimates.

Hit@k=1 if anything relevant is in the top k, else 0 (also Success@k).

Reader: needs one good document — a RAG question with one answering passage. With R=1 it equals Recall@k. Blind spot: binary per query — one of ten relevant documents found counts like all ten; it saturates fast, so systems tie at large k.

F1@k=2·P@k·Recall@kP@k+Recall@k — precision and recall in one number.

Reader: a set of k where both matter: nothing missing, little noise. Blind spot: inherits both — depends on k and on R; ignores the order. Rare for rankings, common for classification.

RR=1/rank of the first relevant document; MRR is its mean over queries.

Reader: reads one result — a search box answer, a voice assistant. Blind spot: ignores everything after the first relevant document; not linear — from rank 1 to 2 costs 0.5, from 5 to 6 costs 0.03.

AP@k=1min(R,k)∑i=1kreli·P@i — the precision at every relevant position, averaged; MAP is its mean over queries.

Reader: wants all relevant documents, and high — a lawyer, a systematic review. It is the area under the precision–recall curve. Blind spot: R in the denominator — a relevant document nobody judged raises AP; with R=1 it is just RR.

DCG@k=∑i=1krelilog2(i+1), NDCG@k=DCG@k/DCG@k of the best order.

Reader: scans from the top and cares how good, not only whether — graded relevance. Blind spot: normalised per query — one relevant document at rank 1 scores 1.0, like ten in the top ten; the gain and the logarithm are conventions; the best order needs every relevant document.

ERR=∑r1rRr∏i<r(1−Ri), Ri=2gi−12gmax — the expected 1/rank at which the reader stops.

Reader: reads down and stops at the first document that satisfies them (a cascade): a perfect document on top makes everything below it almost irrelevant. Blind spot: needs grades and gmax; a model of a user, not their measured behaviour.

bpref=1R∑r(1−|n above r|min(R,N)) over the retrieved relevant r; n — judged non-relevant documents, N of them.

Reader: an evaluation with incomplete judgements — the pool. Unjudged documents are skipped, not counted as misses; only judged non-relevant ones ranked above a relevant one cost. Blind spot: depends on how many non-relevant documents were judged; noisy when there are few.

Click a document to change its grade (0 → 1 → 2 → not judged), move k and R; every tab recomputes on this list.

The reader decides the metric: reads one → MRR · reads all k → Recall@k / Hit@k · scans from the top, with grades → NDCG.

In detail

What each one does not see. None of them knows what the reader does with the list. If the reader stops at the first result, only the first relevant one matters. If the reader takes the top five and reads them all in any order, the order inside the five does not matter at all.

Trap 1: P@k has a ceiling of R/k.

Trap 2: Recall@k only grows with k — compare at one k.

Trap 3: MRR is not linear in the rank.

Block 02 · lexical search

The inverted index and BM25

Inverted index: word → the documents that contain it. A query reads only its own words' lists → milliseconds over billions of documents.

An inverted indexterm → the documents that contain it
A query reads one postings list per word.
In detail

The inverted index. Turn every document into a bag of terms (lecture 1), and store the bag the other way round: for every term, the list of documents that contain it, with the counts — its postings list. A query of three words reads three postings lists and touches only the documents that share a word with it; a collection of a billion pages answers in milliseconds. This structure, not the scoring formula, is why lexical search scales.

BM25 — a sum over the query's words of three parts:

BM25 · Robertson et al. (1994) score(q,d)=∑t∈qidf(t)·tf(t,d)·(k1+1)tf(t,d)+k1·(1−b+b·|d|/avgdl)
  • idf — rare words decide: «KAN» matters, «и» does not
  • k1, saturation — every repeat helps less; the total stays below k1+1
  • b, length — the same count means less in a long document
One term's contributiontf-idf grows forever, BM25 saturates
k1 — how soon the curve flattens; its ceiling is k1+1. b — how far the 3× longer document falls below the average one. The dashed line is a raw count, as in tf-idf.
In detail

Scoring: BM25 (Robertson et al., 1994). A document's score is a sum over the query's words; each word contributes three things, coloured in the formula:

  • idf — how rare the word is. A word in few documents decides the ranking («KAN», «E-1043»); a word in every document («и», "the") adds almost nothing.
  • saturation, k1 — how many times the word occurs. More occurrences help, but each adds less than the previous one, and the total never exceeds k1+1: a document that repeats the word fifty times does not beat one that answers the question.
  • length, b — how long the document is. The count is compared with what is expected at that length: twice in a tweet means more than twice in a book. b=0 ignores length, b=1 corrects for it fully.

The defaults k1≈1.2–2, b=0.75 have survived thirty years; BM25 is still the baseline every neural retriever is compared with.

  • catches exact strings: codes, article numbers, names, fresh terms
  • misses synonyms and paraphrases: «вернуть деньги» vs «возврат средств» — no shared word
  • tokenisation decides which words exist: lower-casing alone moved MRR {bm25_split} → {bm25_lower} on gonzo_ML
In detail

What it catches and what it misses. BM25 finds a document only through shared words. That is its strength where the exact string matters — an error code, an article number, a rare name, a term too fresh for any embedding model: each is one postings list away, and idf makes it decisive. And it is blind to synonyms and paraphrases: "how do I get my money back" and "refund policy" share no word, so the score is zero. Everything before the index decides which words exist — lower-casing, punctuation, stemming or lemmatisation (a dozen forms per word in Russian). On {n_posts} posts of a Russian Telegram channel about ML, with {n_golden} questions about them, lower-casing and dropping punctuation alone moved BM25's MRR from {bm25_split} to {bm25_lower}: the default tokenizer of a popular library splits on spaces only, so «LoRA,» and «lora» were two different words.

If the words do not match, add words: pseudo-relevance feedback, HyDE, doc2query — all of them trust a first guess.

In detail

If the words do not match, add words — briefly, since modern retrievers mostly bridge the gap with vectors (next block). On the query side, pseudo-relevance feedback runs the query, takes the characteristic words of the top results and searches again; HyDE (Gao et al., 2023) asks a language model to write a plausible answer and searches with it. On the document side, doc2query (Nogueira et al., 2019) appends to every passage the questions a model generated for it. All of them trust a first guess: a wrong first page or an invented answer pulls the search further off topic.

Block 03 · vectors

Offline, online, and bi-encoders

  • offline, once per document: encode every document → keep the vectors in a vector store
  • online, per query: encode only the query → look up the nearest vectors (exactly, or with an ANN index)
Offline and onlinethe index is built once; a query only reads it
The same encoder on both lanes; only the lookup grows with the collection.
In detail

Offline and online. Every retriever splits its work in two. Offline, when the collection changes: read every document once and store what the search will need — postings lists for words, vectors for meaning — in an index. Online, per query: process only the query and look the answer up in the index. That is what lets a neural network take part at all: the expensive pass over every document happens once, ahead of time, and a query pays for one forward pass of its own and a lookup. For vectors, the index is a vector store (FAISS, Qdrant, pgvector, …): it keeps the document vectors with their metadata and answers "the k nearest to this vector" — exactly, or approximately and much faster (block 04).

Bi-encoder: each text → one vector, on its own; the score is a dot product. The words need not match — the meaning has to.

A bi-encodereach text alone → one vector → a dot product
Tokens → encoder → token states → mean → one vector. The passage's vector never sees the question.
In detail

Dense retrieval replaces the bag of words with one vector per text. A transformer encoder (lecture 4) reads the text; its token states are pooled — the [CLS] state, or the mean — into a vector e(x)∈ℝd; the score is a dot product or a cosine. This is a bi-encoder: query and document never see each other; each becomes a vector on its own, and they meet only in the dot product. Two texts with no word in common can be close, if the encoder was trained to put them close. That is what makes it fast — and what limits it, as block 06 shows.

Contrastive training: pull (query, its passage) together, push the other passages away. What the model learns depends on which passages it is pushed away from — the negatives.

InfoNCE with in-batch negatives · s — the similarity, τ — a temperature ℒ=−1B∑i=1Blogexp(s(qi,pi)/τ)∑j=1Bexp(s(qi,pj)/τ)
In-batch negativesone matrix product, B × B scores
Diagonal — positives; every other cell — a free negative. The button adds one hard negative per pair.
In detail

How it is trained. A pretrained encoder does not put questions next to their answers by itself: the mean of BERT's token states is a poor retriever out of the box. It is trained contrastively, on pairs (query, relevant passage): pull the pair together, push the query away from passages that are not its own. With a batch of B pairs, the other B−1 passages of the batch serve as negatives for free — in-batch negatives:

Random negatives are easy: a passage about cooking is far from a question about attention anyway. The model learns more from hard negatives — passages that look relevant and are not, typically the top results of BM25 that are not marked relevant. DPR (Karpukhin et al., 2020) added one BM25 negative per question to the in-batch ones; modern models (E5, BGE) are pretrained this way on hundreds of millions of pairs, then fine-tuned on labelled data.

Where the negatives come from — from easy to hard:

  • random — any document · in-batch — the other pairs' passages
  • BM25 — share words with the query, are not the answer
  • hard, by cosine — the model's own nearest neighbours (ANCE)

The harder the negative, the more it teaches — and the likelier it is relevant after all.

Negative miningfrom easy to hard

In detail

Negative mining. The loss pushes the query away from its negatives, and how far they already are decides how much it learns. Random documents are far away: their term in the softmax is already tiny, the gradient is near zero. In-batch negatives are the same random documents, only free — the encoder computed them anyway — and modern models are trained with batches of thousands of pairs precisely to get more of them; a near-duplicate question elsewhere in the batch quietly becomes a negative for its twin. BM25 negatives (DPR, Karpukhin et al., 2020) look relevant by their words: the model learns that word overlap is not enough. The hardest are the model's own mistakes: encode the collection, take each query's nearest neighbours by cosine and use those that are not the positive (ANCE, Xiong et al., 2021). They teach the most and bring two problems. The index is computed with an older version of the model and has to be refreshed during training. And among the nearest neighbours are documents that do answer the question but were never labelled — the incompleteness of the pool, now inside the training data; pushing them away teaches the model to separate true matches. The fixes: re-score the candidates with a cross-encoder and drop the ones it calls relevant (RocketQA, Qu et al., 2021), or drop every candidate whose score comes too close to the positive's (NV-Retriever, Moreira et al., 2024).

Asymmetric models (E5) need prefixes, query: and passage: . A wrong prefix raises no error — the numbers are just lower.

In detail

Symmetric and asymmetric. A question and a passage are different kinds of text. Asymmetric models mark which is which: E5 expects query: before a query and passage: before a document, and was trained so that a query lands near the passages that answer it. Symmetric models (bge-m3, sentence-similarity models) treat both sides the same and are trained on pairs of the same kind as well. Using an asymmetric model without its prefixes, or with the wrong one on the documents, quietly costs quality: nothing fails, the numbers are just lower.

Prefixeswhere the documents land
Encode the documents with query: and the nearest neighbours of a question become question-like documents.

Block 04 · scale

Approximate nearest neighbours

Exact search costs N·d per query. ANN gives up a little recall for orders of magnitude in speed.

In detail

The exact search compares the query with every stored vector: N·d multiplications per query. A million documents at d=1024 is a billion — fine on a GPU for one query, too slow for a service with many. Approximate nearest neighbour (ANN) indexes give up a little recall for orders of magnitude in speed. Three ideas cover most of what vector stores do. The table gives their costs for N vectors of dimension d.

HNSW: a layered graph; a greedy walk from the sparse top layer down — about logN hops.

HNSWa greedy walk, layer by layer
Start on the sparse top layer, always step to the neighbour closest to the query, descend.
In detail

HNSW — a hierarchical navigable small-world graph: every vector is linked to its M nearest neighbours, in several layers from sparse to dense; a vector reaches layer l with probability decaying exponentially in l, so there are about logN layers. A search starts at the top and walks greedily towards the query, descending a layer whenever no neighbour is closer. Each layer costs a few hops, so a query costs O(logN) hops in practice (the logarithm is empirical, not a guarantee); building inserts every vector with the same walk, O(NlogN). The fastest at high recall; the price is memory — the graph sits next to the full vectors — and ef, the width of the walk, which trades recall against time.

IVF: k-means cells; search only the nprobe cells nearest to the query. A neighbour across a border is lost.

IVFprobe the nearest cells only
Shaded — the probed cells; ringed — the true top 10, green found, red missed. Move nprobe, or click the map.
In detail

IVF, the inverted file: cluster the vectors with k-means into C cells; at query time compare the query with the C centroids and look only into the nprobe nearest cells. The inverted index again, with cells instead of words. A true neighbour that sits across a cell border is lost unless its cell is probed.

In 1024 dimensions the neighbours scatter: on gonzo_ML one cell of {ivf_cells} finds {ivf_r1} of the true top 10; {ivf_r_big} costs {ivf_s_big} of the collection.

IVF on real vectorsrecall of the exact top 10 by n_probe
bge-m3 vectors of gonzo_ML: recall of the true top 10 (blue) and the share scanned (grey), by nprobe.
In detail

Two dimensions flatter IVF: there a query's neighbours sit in one or two cells. In high dimension they scatter. On the {ivf_n} bge-m3 vectors of the gonzo_ML posts and their chunks (d = {ivf_d}), with {ivf_cells} cells and the {ivf_nq} questions as queries, one probed cell returns {ivf_r1} of the true top 10; {ivf_r_big} needs {ivf_np_big} cells — {ivf_s_big} of the collection scanned. That is why a real IVF index has thousands of cells and probes dozens, and why its nprobe has to be tuned on your own vectors.

PQ: cut the vector into m pieces, replace each by the id of its nearest centroid → 4 KB becomes m bytes.

Product quantisation4 KB → m bytes
Each of the 8 pieces → the index of its nearest centroid: 4096 bytes → 8.
In detail

PQ, product quantisation: split each vector into m pieces and replace every piece with the id of its nearest centroid among 256 — one byte. A d=1024 float vector, 4 KB, becomes m bytes; distances are computed from small tables of piece-to-centroid distances, without decompressing. Combined with IVF (IVF-PQ) it fits a billion vectors into one machine's memory, at some cost in accuracy.

Filters (date, language, access rights): filter after the top k → often nothing left; filter during the search → the k best that pass.

In detail

Filters. Real queries come with conditions — a date, a language, a user's access rights. Filtering the top k after the vector search (post-filtering) returns nothing when the condition is rare; filtering during it needs an index that supports it. Every vector database answers this differently, and it is worth checking before choosing one.

Block 05 · both

Hybrid search and rank fusion

BM25 and dense search fail on different queries → run both and merge. The scores live on different scales → merge the ranks.

Reciprocal rank fusion · Cormack et al. (2009) RRF(d)=∑m∈retrieverswmc+rankm(d)
In detail

Lexical and dense search fail on different queries: one on paraphrases, the other on codes and fresh names. Running both and merging the lists is the cheapest improvement there is. The question is how to merge.

Adding the scores does not work as such: BM25 runs from zero with no upper bound, and its scale changes from query to query with the number and rarity of the words; a cosine sits in [−1,1], usually in a narrow band. Min-max normalisation per query is possible but fragile — one outlier squeezes all the others. Reciprocal rank fusion (Cormack et al., 2009) ignores the scores and adds up ranks:

c=60: rank 1 is worth only ×{rrf_ratio12} of rank 2; rank 10 keeps {rrf_w10} of rank 1. Being in both lists beats being first in one.

The weight of a rank1 / (c + r), relative to rank 1
The weight of a rank relative to rank 1: your c (solid) and c=0 (dashed).
In detail

What c does. Rank r is worth 1/(c+r). The constant decides how much the fusion cares about a difference in rank: the first place is worth (c+2)/(c+1) times the second. With c=0 that is twice as much — one list's favourite dominates the sum. With c=60, the default from the paper, it is {rrf_ratio12} times; even the tenth place keeps {rrf_w10} of the first one's weight. So RRF with c=60 hardly hears the order inside the top of a list and hears loudly whether a document is in the list at all, and in how many: a document that both retrievers put in their top ten beats one that only one of them put first. A smaller c trusts each list's top positions more. The price either way: RRF does not know how far the first document was ahead of the second.

Block 06 · the second stage

Cross-encoders, late interaction, cascades

Where the query meets the document:

  • no interaction — bi-encoder: one vector each, a dot product
  • late — ColBERT: a vector per token each, MaxSim
  • early — cross-encoder: one transformer reads both texts

In detail

Where the query meets the document. The neural retrievers differ by when the two texts first see each other.

  • No interaction — the bi-encoder (block 03). Each text becomes one vector on its own; they meet only in a dot product. The whole passage is compressed before anyone knows the question, and whatever the question will ask about must survive that compression.
  • Late interaction — ColBERT (Khattab & Zaharia, 2020). Each text becomes a vector per token, still on its own; they meet at the very end, in MaxSim: every query token finds its best match among the document's tokens, and the matches are summed. Finer than one vector — a rare term in the query can find its token in the passage — and still precomputable.
  • Early interaction — the cross-encoder (Nogueira & Cho, 2019). Query and passage are concatenated, [CLS] query [SEP] passage, and read by one transformer: from the first layer on, every token of one attends to every token of the other, and the [CLS] state becomes a relevance score. It sees the pair — negation, which entity, which sentence answers — and is the most accurate of the three.

A cross-encoder is slow: a forward pass per pair, nothing precomputed — {rr_s_pair} s per pair on an M4: {rr_full} s for all {n_docs} posts, {rr_top20} s for a top 20.

In detail

Why a cross-encoder is slow. A bi-encoder's cost per query does not depend on the collection: one forward pass for the query, then arithmetic on stored vectors. A cross-encoder's cost is one forward pass per pair, and each pass reads query and passage together, with attention quadratic in their joint length. Nothing of it can be reused for the next query, because every hidden state of the passage depends on the question. Measured: {rr_model} ({rr_params} parameters) on an Apple M4 scores one pair in {rr_s_pair} s. Over the {n_docs} documents of gonzo_ML that is {rr_full} s for a single query; over a first stage's top 20 — {rr_top20} s.

  • ranking — the whole collection, cheap per document; the goal is recall
  • reranking — a short list, expensive per document; the goal is precision at the top, and it cannot add what was missed
  • → a cascade: a cheap top 20–100, then the cross-encoder
In detail

Reranking is a different task from ranking. Ranking orders a whole collection: it must be cheap per document, run from an index, and its job is recall — not to lose the relevant document somewhere among millions. Reranking orders a short list somebody else made: it can afford an expensive model per item, its job is precision at the top — what comes first — and it cannot add anything: what the first stage missed is gone. So a reranker is judged by MRR or NDCG@10 over its input, and its ceiling is the first stage's recall at the depth it reads. Hence the cascade: a cheap retriever selects the top 20–100 out of millions; the cross-encoder reorders only those. And on a short list, models that compare candidates with each other (pairwise, listwise, a language model reading all of them) become affordable too.

In detail

The arithmetic of the cascade decides how deep the first stage goes. On this corpus the first stage already puts first every post it finds in its top 10 — its MRR, {cas_first}, equals its Hit@10 — so up to depth 10 the reranker has nothing to fix (at depth 2 it even demotes one post). Its whole gain comes from depth: the three remaining posts sit at ranks {cas_ranks} of the fused list, and once the reranker reads them (depth {cas_full}) MRR rises to {cas_mrr_full}. Reading 50 adds nothing. The depth is set by where the first stage's recall stops growing, not by the reranker.

Block 07 · the application

Retrieval for a language model

RAG = retrieve → put into the prompt → answer from it. The knowledge moves from the weights to the index: updatable, restricted per user, citable.

In detail

A language model knows what was in its training data, up to its cutoff, and invents fluently past it. Retrieval-augmented generation (Lewis et al., 2020) puts the search in front: retrieve the passages for the question, put them into the prompt, let the model answer from them. The knowledge moves from the weights to the index, where it can be updated, restricted per user and cited. Everything on this page is the first half of that pipeline.

When the reader is a model:

  • the budget is the context window → Recall@k at a small k
  • it has to notice when the context is not enough
  • the position in the prompt matters (lost in the middle)
  • two evaluations: did retrieval bring the passage, did the model answer from it
In detail

What changes when the reader is a model rather than a person:

  • the budget is the context window and the cost per token: the top k goes in whole, so Recall@k at a small k is the number that matters, and precision costs money;
  • the model has to notice when the context is not enough — a ranking always has a first document, and a model given a context tends to use it. "Answer only from the context, say so if it is not there" in the prompt helps; a second call that judges whether the context suffices (corrective RAG) helps more; a threshold on the best similarity is the obvious fix and rarely works, because the scores of answerable and unanswerable questions overlap;
  • where a passage sits in the prompt matters: models use the beginning and the end of a long context better than its middle (Liu et al., 2024, "lost in the middle");
  • two evaluations, not one: did the retriever bring the right passage (the metrics of block 01), and did the model answer correctly from it (faithfulness to the context, correctness of the answer). A wrong answer with the right passage in the context is the generator's failure; a wrong answer without it is the retriever's.
