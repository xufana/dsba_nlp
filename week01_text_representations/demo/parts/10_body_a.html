Block 01 · tokenization

Where the vocabulary comes from

First, we need to split the text into parts in a way that will represent the text, its meaning and properties. It is called tokenization. Tokenization splits a string into units. The set of units becomes your vocabulary, and the vocabulary decides what kind of data the model can possibly represent.

Four tokenizers, one string
Read what each one did. Only word_tokenize keeps alex.smith_92 and hse.ru intact; the others shred an identifier into five pieces no downstream model can put back. regex keeps smith_92 because _ is a word character while naive splits it because _ is in string.punctuation — nobody designed that disagreement. 3.5% becomes 3, 5; on a financial corpus that is the signal being deleted. And Don’t → Do + n’t is not a split at all: it is a rewrite. It is not a tokenization error, it is a design choice. The tokenizer’s design choices are the model’s design choices, and we'll talk about it later in more detail during the course (I believe, week 4 or 5?)
in codenltk.tokenize · word_tokenize · wordpunct_tokenize · re.findall · spaCy 
import re, nltk
from nltk.tokenize import word_tokenize, wordpunct_tokenize

re.findall(r"\w+", text)          # the regex tokenizer above
wordpunct_tokenize(text)          # splits on every non-word character
word_tokenize(text)               # Treebank rules: needs nltk.download("punkt_tab")
word_tokenize is the one that rewrites rather than splits. For production text pick by what your downstream step needs: spaCy for linguistically-aware splitting, regex for speed, a trained subword tokenizer for anything that feeds a neural model.

Stemming and lemmatization

But first, stemming & lemmatization. Why? Cuz we need to shrink the vocabulary a bit and get rid of the noise. The textbook table says went → go and better → good. Bet first: does nltk’s lemmatizer reproduce it?

nltk · WordNetLemmatizer + PorterStemmertextbook vs. reality
Commit to an answer, then look.
in codenltk.stem · PorterStemmer · WordNetLemmatizer · nltk.pos_tag · pymorphy3 
from nltk.stem import PorterStemmer, WordNetLemmatizer

PorterStemmer().stem("studies")            # 'studi' — rules, no dictionary
WordNetLemmatizer().lemmatize("was")       # 'wa'    — pos defaults to 'n'
WordNetLemmatizer().lemmatize("was", "v")  # 'be'    — with the right tag
Real lemmatization needs POS tags, so in practice you run a tagger first — nltk.pos_tag, or spaCy, which gives you token.lemma_ already tagged. For Russian: pymorphy3 or spaCy's ru_core_news_*.
It does not. went → went, better → better, and was → wa, which is not a word in any language. The default is pos='n': the lemmatizer assumes every token is a noun and strips what looks like a plural. The textbook table describes lemmatization with part-of-speech tags. The column you usually see in a tutorial is lemmatization without them — a different operation, and on this corpus roughly an expensive stemmer with worse coverage. So, overall it works as intended, depending on the library you're using and other nuances. This is also a part of a design choice (sometimes you'll need it, sometimes you'll lose the important information using it)

Block 02 · preprocessing

To clean or not to clean

The usual advice is “clean your text”. The usual advice is wrong roughly half the time.

Where you must not skip it

LDA (Latent Dirichlet Allocation) is a bag of words with no notion of synonymy or morphology. Feed it raw text and end up with the topics that are described primarly by the most frequent words like the, and, for. Let's compare:

LDA · topics · raw vs lemmatised
in codesklearn.decomposition.LatentDirichletAllocation · gensim.LdaModel · CoherenceModel · BERTopic 
from sklearn.feature_extraction.text import CountVectorizer
from sklearn.decomposition import LatentDirichletAllocation

X = CountVectorizer(max_df=0.95, min_df=5).fit_transform(docs)
lda = LatentDirichletAllocation(n_components=8, random_state=42).fit(X)
lda.components_          # topic × term weights; sort each row for the top words
gensim.models.LdaModel is the other standard implementation and gives you coherence scores (CoherenceModel) to pick the number of topics; BERTopic is the modern embedding-based alternative. All of them are bags of words, so the preprocessing decision above applies to every one.
39 is a mangled &#39; and quot a mangled &quot;. Here preprocessing is not a tuning knob — it is the difference between a model that works and a model that models punctuation. Same for lexical search (cats will not find cat), dictionary methods, and small data. Question: would you also try lemmatization here for this task?

not good becomes good; never recommend becomes recommend. That is the mechanism. Whether it costs you accuracy is a different question, and the grid below answers it with numbers instead of folklore.

Which cleaning, for which task

Twelve A/B experiments over six datasets and four task families. Each one flips a single knob and holds everything else fixed — same split, same seed, same model, same vectorizer — so the difference belongs to the knob and to nothing else.

Bet on every row before you reveal. Three answers per row: the cleaning helps, it hurts, or it changes nothing (under half a point). The rows are ordered so that the same knob comes back on a different task.

def ab(analyzer):                 # one knob; split, seed, model all fixed
    v = TfidfVectorizer(analyzer=analyzer, min_df=2)
    X = v.fit_transform(train_texts)
    m = LogisticRegression(max_iter=2000, random_state=42).fit(X, y_train)
    return m.score(v.transform(test_texts), y_test)

plain  = lambda t: re.findall(r"(?u)\b\w\w+\b", t.lower())
nostop = lambda t: [w for w in plain(t) if w not in stop]

ab(nostop) - ab(plain)            # the delta is the whole answer
The comparison is only worth anything if the two runs differ in exactly one place: same train/test split, same random seed, same classifier, same min_df. Building TF-IDF by hand, understanding how does the vector look like

Before running anything on 120 000 documents, build the thing on four. Every number below is computed in your browser with sklearn’s exact formulas — edit the documents and watch the matrix move.

The vectorizer, stage by stage
in codesklearn.feature_extraction.text · CountVectorizer · TfidfVectorizer · rank_bm25 
from sklearn.feature_extraction.text import CountVectorizer, TfidfVectorizer

CountVectorizer(min_df=4)                                   # the raw counts
TfidfVectorizer(min_df=4, max_df=0.95)                      # the five stages above
TfidfVectorizer(min_df=4, ngram_range=(1, 2))               # + bigrams
TfidfVectorizer(min_df=4, analyzer="char_wb", ngram_range=(3, 5))

vec.idf_, vec.get_feature_names_out()   # the two arrays that explain any row
The defaults matter more than the class: lowercase=True, token_pattern=r"(?u)\b\w\w+\b" (one-character tokens are dropped), norm="l2", and the smoothed IDF you see in stage 3. For retrieval rather than classification, reach for BM25 instead — rank_bm25, or Elasticsearch/OpenSearch.

What the bag threw away in step zero

Bet: two headlines, the same five words, opposite meaning. What is the cosine similarity of their TF-IDF vectors?

Word order · cosine similarity
To a bag of words those two headlines are the same document. One says oil fell and stocks rose; the other says the opposite. No classifier on top can tell them apart. Bigrams buy the local part of word order back — and on AG News take the vocabulary from 29 350 to 196 911 for +0.002 accuracy. On a task where order carries the label — sentiment, negation, intent — the same change is worth far more.
